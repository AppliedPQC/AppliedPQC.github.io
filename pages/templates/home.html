{{ _("Why it matters") }}

{{ _("Shor's algorithm, run on a cryptographically relevant quantum computer, recovers private keys from public ones. NIST's transition schedule names every public-key algorithm that falls to it:") }}

  • {{ _("RSA, for encryption and signatures") }}
  • {{ _("ECDSA and EdDSA, the signatures behind TLS certificates, SSH keys and blockchains") }}
  • {{ _("Diffie-Hellman, over finite fields and elliptic curves, X25519 included") }}
  • {{ _("MQV, an authenticated key agreement") }}

{{ _("The two halves fail on different clocks. Key exchange is exposed today, because ciphertext recorded now can be decrypted once the machine exists: harvest now, decrypt later. Forging a signature needs the machine at the time of the forgery, so authentication becomes urgent when the machine is near. Long-lived keys, such as roots of trust and firmware signing keys, are the exception.") }}

{{ _("The takeaway.") }} {{ _("Anything that must stay secret into the 2030s should be using post-quantum key exchange already. That is why deployment so far is almost entirely key exchange.") }}

{{ _("The deadlines") }}

{{ _("Governments have turned the standards into dates. They differ in detail and agree on the end: by 2035, nothing quantum-vulnerable should be left.") }}

  1. 2024{{ _("FIPS 203, 204 and 205 published") }}
  2. 2026{{ _("EU: national strategies and inventories started") }}
  3. 2027{{ _("France: PQC required in newly qualified products. NSA: new national security system purchases quantum-resistant") }}
  4. 2028{{ _("UK: discovery and migration plan done") }}

  7. 2035{{ _("NIST disallows them. US, EU and UK migrations complete") }}

{{ _("What has shipped") }}

{{ _("Post-quantum cryptography is no longer a research project. These are released versions and live services, not announcements.") }}

1{{ _("Key exchange: on by default") }}

  • {{ _("OpenSSH has used mlkem768x25519-sha256 by default since 10.0.") }}
  • {{ _("Apple's operating systems, from version 26, offer X25519MLKEM768 from URLSession and the Network framework, so every app on those APIs sends a hybrid key share.") }}
  • {{ _("Java: JDK 27 puts X25519MLKEM768 first in its default TLS 1.3 groups.") }}
  • {{ _("Cloudflare leads with X25519MLKEM768 to every origin that speaks it, which moved some 45 billion daily connections without customer action.") }}
  • {{ _("Signal uses X25519 with ML-KEM-1024 for initial key agreement, and extends that protection into the ratchet.") }}

2{{ _("Libraries: in the standard ones") }}

  • {{ _("OpenSSL has native ML-KEM, ML-DSA and SLH-DSA since 3.5. 4.1 (October 2026) makes them faster.") }}
  • {{ _("Go has crypto/mlkem since 1.24, and 1.27 adds crypto/mldsa and ML-DSA in X.509 and TLS, with no third-party dependency.") }}
  • {{ _("rustls prefers X25519MLKEM768 since 0.23.27 and enables ML-DSA certificates since 0.23.44.") }}
  • {{ _("AWS-LC ships mlkem-native, whose assembly is proved correct and constant-time in HOL-Light. BoringSSL holds Chrome's ML-KEM.") }}
  • {{ _("liboqs and Bouncy Castle cover the widest range of algorithms, in C and on the JVM.") }}

3{{ _("Authentication: the harder half") }}

{{ _("An ML-DSA-44 signature is 2,420 bytes, against 64 for ECDSA, and a TLS handshake carries several. So the web is not simply swapping algorithms in its certificates.") }}

  • {{ _("Chrome will not add post-quantum X.509 chains to its root store. It is building a separate store for Merkle Tree Certificates instead, in phases through 2027.") }}
  • {{ _("Let's Encrypt chose Merkle Tree Certificates in June 2026, and Cloudflare is becoming a public CA to issue them free from early 2027.") }}
  • {{ _("OpenSSH 10.6 made ML-DSA-44 with Ed25519 a regular key type, and 10.6p2 accepts it for SSH certificate authorities.") }}
  • {{ _("Cloudflare's 1.1.1.1 resolver validates ML-DSA-44 DNSSEC signatures.") }}

{{ _("Private PKI can move now: rustls, Go and OpenSSH all accept ML-DSA certificates you issue yourself. The public web cannot until browsers trust a post-quantum CA.") }}

{{ _("What to do now") }}

{{ _("Start with an inventory.") }} {{ _("Every timeline above assumes you can say where RSA and the elliptic curves are in your systems. Most organisations cannot yet.") }}

  1. {{ _("Find the vulnerable cryptography.") }} {{ _("A static scan cannot see dynamically loaded code, vendored binaries or hardware modules, so zero findings means nothing matched, not that nothing is there.") }}
  2. {{ _("Turn on hybrid key exchange.") }} {{ _("Current TLS and SSH stacks already offer it. Check that your middleboxes accept the larger handshake.") }}
  3. {{ _("Test against NIST's vectors.") }} {{ _("An implementation is not correct because it agrees with itself. NIST's ACVP vectors carry inputs and expected outputs for ML-KEM, ML-DSA and SLH-DSA.") }}
  4. {{ _("Plan signatures on a longer clock.") }} {{ _("Private PKI can issue ML-DSA certificates today. Public certificates wait for Merkle Tree Certificates, from 2027.") }}

{{ _("Questions") }}

{{ _("Is FN-DSA (Falcon) a standard yet?") }}

{{ _("No. NIST lists FIPS 206 as in development, with no public draft and no test vectors. Until it appears the round-3 Falcon submission is the specification, which is why Algorand's signatures are Falcon rather than FN-DSA.") }}

{{ _("Does my connection already use post-quantum cryptography?") }}

{{ _("Probably, for key exchange, if both ends are current: Apple's OS 26 networking, JDK 27, OpenSSH 10 and Cloudflare all offer a hybrid by default. The certificate that authenticates the connection is still classical.") }}

{{ _("Should I use a hybrid or post-quantum alone?") }}

{{ _("It depends on whose guidance you follow. BSI and ANSSI insist on hybrids, NCSC prefers pure post-quantum, and NIST accepts either in FIPS 140. For signatures, RFC 9955 sets out what each kind of hybrid does and does not protect.") }}

{{ _("Is Classic McEliece still recommended?") }}

{{ _("Not for new work in Germany. In October 2026 BSI recommended against it for new developments after new cryptanalysis, while stating that no practical attack exists, and named ML-KEM and FrodoKEM as preferred. It is the first reversal of a national PQC recommendation.") }}

{{ _("Are hash-based signatures safe to deploy?") }}

{{ _("They rest on the most conservative assumption there is. SLH-DSA is stateless and can be used like any signature. LMS and XMSS are stateful: signing twice with one key allows forgeries, so they belong where state is managed carefully, such as firmware signing.") }}

{{ _("When will a quantum computer break RSA?") }}

{{ _("Nobody can say, and none of the deadlines above is a forecast of it. They are planning dates, set by how long a migration takes.") }}
